# 企業内 DFIR コンソールとしての hayabusa-plus

最終更新: 2026-10-22

この文書は、hayabusa-plus を「個人が自分の PC を調べるツール」から
「組織の調査チームが、隔離した解析ホストで使う DFIR コンソール」へ移行するための
設計メモです。商用 DFIR 製品の公開資料から、無料で再実装できる価値を整理し、
現在の実装と今後の差を明示します。

---

## 1. 結論

hayabusa-plus は次の 3 点に絞ると、企業内で説明しやすい無料の DFIR 基盤になります。

1. **解析対象端末の上で動かさない。** 収集は EDR / Velociraptor / KAPE /
   既存の収集スクリプトに任せ、解析は WSL2 または Linux の専用ミニ PC で行う。
2. **証跡の同一性を先に記録する。** 取込時に SHA-256 とサイズを残し、
   ディレクトリは manifest ハッシュにする。解析結果より先に「何を読んだか」を固定する。
3. **案件単位で追跡する。** ケース、証跡、スキャン、監査イベントを結び、
   ジョブを消しても証跡台帳と監査ログは残す。

認証・SSO・RBAC・遠隔収集・WORM 保管は、このリポジトリだけでは完結しません。
企業導入では前段の VPN / リバースプロキシ / 認証基盤、または Velociraptor 等の
収集基盤と組み合わせます。**足りない機能を嘘で埋めず、境界を明記する**のが方針です。

---

## 2. 前提とする脅威モデル

### 2.1 同一端末解析を避ける理由

侵害された端末上で解析ツールを実行すると、次の問題が起きます。

- マルウェアが解析プロセスを監視・妨害・改ざんできる
- 端末の時刻、DLL、証明書ストア、DNS が攻撃者の制御下に入り得る
- 解析ツール自身が EDR に検知され、対応の証拠を汚す
- メモリ・ディスクの状態を「読む」行為が証拠を変化させる
- 管理者権限の昇格や横展開の足場を、解析作業が作ってしまう

したがって、標準運用は **収集 → 解析ホストへ転送 → ハッシュ検証 → 解析** です。
本コンソールは解析ホスト自身のログを直接読む機能を持たず、収集済みの
EVTX / ZIP のみを取り込みます。

### 2.2 USB 対 USB を避ける理由

USB メディアは、次の理由で企業 DFIR の標準経路にしにくいものです。

- 収集端末と解析端末の間でマルウェアを持ち運ぶ
- メディアの紛失・すり替え・書き込み混入が起きる
- どのファイルを誰が搬送したかが台帳化されない
- USB 自動実行やドライバ経由の攻撃面がある

どうしても必要な場合は、ライトブロッカー、専用媒体、ラベル、受渡書、
SHA-256 の照合、そして解析ホスト側での再ハッシュを必須にします。
ネットワーク転送でも、暗号化された専用 VLAN / VPN / ジャンプホストを使います。

### 2.3 このコンソール自身の脅威モデル

- 既定は `127.0.0.1` バインド。認証はない。
- `--shared` / `-Public` は明示的な opt-in なしでは起動しない。サーバ本体も非 loopback バインドを拒否する。
- 公開モードの匿名クライアントは、アップロード・スキャン・ランキング以外の API を参照できない。
- データ領域は `HAYABUSA_DATA_ROOT` で分離でき、`umask 077` で作る。
- 監査ログはハッシュチェーンだが、ホスト全体を書き換えられる攻撃者には耐えない。
- 完全な改ざん防止には、外部 SIEM / WORM / 別ホストへのエクスポートが必要。

## 3. 参照アーキテクチャ

```
[ 収集対象 ]                [ 転送 ]                    [ 解析ホスト ]                 [ 保管・連携 ]
 EDR / Velociraptor   →   暗号化 VLAN / VPN      →   WSL2 または Linux mini-PC   →   ケースレポート
 KAPE / 収集スクリプト      ジャンプホスト             ・hayabusa-plus (localhost)       Elastic / SIEM
 ライトブロッカー           ハッシュ照合               ・ext4 / LUKS データ領域           WORM / 証跡保管
                                                        ・監査ログ (hash chain)
```

### 3.1 配置

| 配置 | 用途 | 注意 |
|---|---|---|
| WSL2 (Windows 11) | 開発・検証・小規模案件 | `/mnt/c` は遅く、Windows 側から見える。証跡は ext4 VHD へ |
| Linux mini-PC | 本番の解析ホスト | 専用ユーザー、全ディスク暗号化、GUI は localhost のみ |
| 隔離 VLAN のサーバ | チーム共用 | 前段に認証付きリバースプロキシ / VPN。直接公開しない |
| エアギャップ | 高度機密・マルウェア案件 | 更新は署名済み媒体で。時計同期とログ持ち出しを統制 |

### 3.2 データ領域

`HAYABUSA_DATA_ROOT`（または `HAYABUSA_WORKSPACE`）を指定すると、
DB・アップロード・ジョブ・監査ログをリポジトリ外に置けます。

```bash
DATA_ROOT=/srv/dfir /path/to/hayabusa-plus/start.sh
```

推奨:

- 証跡用の ext4 ボリューム（可能なら LUKS 暗号化）
- 解析ホストの OS 領域とは別ディスク
- OneDrive / Dropbox / 共有フォルダをデータ領域にしない
- 容量監視と、案件終了後の保全・削除手順を決める

### 3.3 ネットワーク

- 既定: `127.0.0.1`。WSL2 の localhost forwarding のみ。
- チーム共用: 解析ホストを隔離 VLAN に置き、VPN / 認証プロキシ経由。
- インターネット公開はしない。ランキング機能は「閉じた勉強会」用途に限定。
- 外向き通信は、IoC フィード取得を明示的に許可した場合だけ。

## 4. 商用・OSS DFIR 製品から取り込む価値

以下は各製品の公開資料に基づく **代表的な機能の整理** です。価格や契約条件は
変わるため、導入時にベンダーへ確認してください。ここでの目的は「何を無料で
再実装できるか」を決めることです。

| 能力 | 商用製品の例 | OSS の例 | hayabusa-plus の状況 |
|---|---|---|---|
| ケース / 案件管理 | Magnet AXIOM Cyber, Cyber Triage, DFIRe | Timesketch sketch, IRIS | **実装済み（軽量）** |
| 証跡の同一性 | AXIOM Cyber, DFIRe | 手動 + ハッシュ | **実装済み（SHA-256 / manifest）** |
| 監査証跡 | DFIRe, 企業向け DFIR 基盤 | Timesketch の操作履歴 | **実装済み（hash chain）** |
| 遠隔収集 | AXIOM Cyber, CrowdStrike Falcon Forensics, Velociraptor | Velociraptor | 対象外。外部収集と連携 |
| タイムライン分析 | AXIOM Cyber, Timesketch | Timesketch | 検知タイムライン + ログ検索 |
| ハント / ノートブック | Velociraptor, Timesketch | Velociraptor | 検知ハント + プロセスツリー |
| マルウェア / IoC | AXIOM Cyber, CrowdStrike | OpenCTI, MISP | IoC フィード + Sigma 照合 |
| RBAC / SSO | 商用 DFIR 基盤 | Django / OIDC 連携 | **未実装。前段で補う** |
| マルチテナント | Velociraptor orgs, 商用基盤 | 構成次第 | **未実装** |
| WORM / 法的証拠保全 | 商用フォレンジック基盤 | 外部アーカイブ | **未実装。外部保管へ** |
| レポート出力 | AXIOM Cyber, DFIRe | Timesketch | HTML サマリ + JSON/CSV |

### 4.1 Magnet AXIOM Cyber から学ぶ点

公開資料では、リモート収集、ケースインテリジェンス、YARA / MITRE ATT&CK 連携、
エビデンスの一貫性を前面に出しています。特に **「収集と解析を分離し、案件単位で
エビデンスを束ねる」** という考え方は、無料ツールでも真似できます。

### 4.2 Cyber Triage から学ぶ点

トリアージの高速化、判断の標準化、レポートの定型化が中心です。
hayabusa-plus の「検知を日本語で解説し、TP/FP を記録する」流れは、
このトリアージ体験の無料版として位置づけられます。

### 4.3 CrowdStrike Falcon Forensics から学ぶ点

エージェント基盤とクラウド側の収集・解析の分離、組織的な可視性が強みです。
hayabusa-plus はエージェントを作らず、**既存 EDR の収集結果を受ける側**に徹します。

### 4.4 Velociraptor から学ぶ点

- クライアント / フロントエンド / GUI / API の分離
- ハント（多数端末への一括照会）とノートブック
- 組織（org）単位のマルチテナント
- サーバ側で収集を統制し、端末側の負荷と通信を管理する

hayabusa-plus は Velociraptor の代替ではなく、**収集後の EVTX を深く読む解析面** です。
大規模環境では Velociraptor で収集し、本コンソールで Sigma 検知と日本語トリアージを
行う組み合わせが現実的です。

### 4.5 Timesketch から学ぶ点

- sketch = 案件、timeline = 証跡、view = 保存検索
- 複数アナリストでのタイムライン共有
- 分析結果をストーリーとして残す

hayabusa-plus のケース / 監査 / 検知一覧は、この「案件に文脈を束ねる」考え方の
最小実装です。大規模なタイムライン共同編集は Timesketch に任せます。

### 4.6 DFIRe から学ぶ点

公開資料では、ケース、フェーズ、アクション、ノート、証跡、インジケータ、レポートを
一つの事件として扱い、ケースタイプごとのプレイブックを提供しています。
無料ツールで全部を作るのではなく、**ケース → 証跡 → スキャン → 監査 → レポート**
の縦線を切らないことが重要です。

## 5. 無料で実装する優先順位

### P0: すでに入った基盤

- WSL2 / Linux 優先の起動スクリプト
- localhost 既定、共有モードの明示 opt-in
- データルート分離（`HAYABUSA_DATA_ROOT`）
- ケース（案件名 / 参照番号 / 説明）
- 証跡台帳（ファイル名、サイズ、SHA-256、ZIP 内ファイル数）
- スキャン前の証跡ハッシュ（ファイル / ディレクトリ manifest）
- 追記専用・ハッシュチェーン監査ログ
- ケース / 証跡 / 監査の UI
- ジョブ削除後も証跡台帳を保持

### P1: 次の実装候補

- ケースレポートの HTML / JSON エクスポート（証跡ハッシュと検知サマリを含む）
- 証跡の再ハッシュ検証（保管中に変化していないか）
- 監査ログの外部エクスポート（SIEM / WORM）
- 抑制・TP/FP 判定の監査イベント化
- ケースのクローズ / 再オープンと保持期限
- Elastic へのケースメタデータ投入

### P2: 企業導入時に前段・別製品で補うもの

- OIDC / SAML SSO、RBAC、監査可能な操作制御
- TLS 終端とリバースプロキシ
- マルチテナント / 組織分離
- リモート収集エージェント（Velociraptor 等）
- WORM ストレージ、法的ホールド、保存暗号化
- HA、バックアップ、署名済みアップデート

## 6. 証跡と監査のモデル

### 6.1 証跡（evidence）

アップロード時:

- 元ファイル名、保存先、サイズ
- 元ファイルの SHA-256
- ZIP の場合は展開後の EVTX 数
- 受領時刻、ケース ID（指定時）

スキャン時:

- 実際に Hayabusa が読む対象の SHA-256
- ディレクトリの場合は、ソート済みの
  `<sha256>  <size>  <relative-path>` 行に対する manifest ハッシュ
- ファイル数、合計バイト数、ハッシュ時刻

これにより「アップロードした ZIP」と「解析した展開ディレクトリ」の両方を
説明できます。ジョブを削除しても証跡台帳は残ります。

### 6.2 監査ログ（audit）

`<data-root>/audit/audit.jsonl` に 1 行 1 イベントで追記します。

```
hash = SHA-256(prev_hash + "\n" + canonical_json(payload))
```

記録する例:

- `case.open`
- `evidence.upload`
- `evidence.hash`
- `scan.requested` / `scan.start` / `scan.finish`
- `suppression.create` / `suppression.delete`
- `job.delete` / `jobs.clear`

UI の「ハッシュチェーンを検証」で、途中の行の改変・欠落を検出できます。

**限界:** ローカルのハッシュチェーンは、ホスト全体を支配した攻撃者による
全ファイル書き換えまでは防げません。企業の保持要件では、監査ログを
外部 SIEM / WORM / 別ホストへ定期エクスポートしてください。

## 7. 運用ランナー（例）

1. **案件起票**: ケース名（例 `IR-2026-042`）、参照番号、対象範囲を登録。
2. **収集**: EDR / Velociraptor / KAPE で EVTX を取得。収集側でも SHA-256 を記録。
3. **搬送**: 暗号化 VLAN / VPN / ジャンプホスト。USB は最終手段。
4. **取込**: ケース名を指定してアップロード。元ファイルの SHA-256 を確認。
5. **解析**: スキャン実行。開始前に証跡ハッシュが記録される。
6. **トリアージ**: 検知一覧、プロセスツリー、ログ検索、ハントで確認。
7. **判定**: TP/FP を記録し、必要なら抑制理由を残す。
8. **報告**: HTML サマリ / CSV / JSON を案件レポートへ添付。
9. **保管**: データ領域と監査ログを保持期限まで保全。外部へハッシュをエクスポート。
10. **削除**: 保持期限後に、証跡・ケース・監査の削除手順を記録して実施。

## 8. 導入チェックリスト

- [ ] 解析対象端末と解析ホストが別である
- [ ] 解析ホストの UI は localhost または認証付き前段のみ
- [ ] データ領域は暗号化され、共有フォルダではない
- [ ] 収集側と解析側の両方で SHA-256 を記録している
- [ ] 監査ログを外部へエクスポートしている
- [ ] ケースの保持期限と削除手順が文書化されている
- [ ] IoC フィード取得の外向き通信を許可制にしている
- [ ] Elastic 連携を使う場合、認証情報と保存先を分離している
- [ ] 直接読取機能を持たず、収集済み EVTX / ZIP のみを取り込むと周知している
